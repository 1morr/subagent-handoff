## 訂閱線的節流重試：純損耗

同一份記錄裡，22 筆觸發了重試機制：

| 指標 | 數字 |
| --- | --- |
| 在訂閱線 | 22 / 22（100%） |
| 狀態是 429 | 22 / 22（100%） |
| 三次嘗試全部失敗 | 22 / 22（100%） |
| 帶了 `retry-after` | 0 / 22 |
| 同期第三方線的 5xx 或連線錯誤 | 0（共 1668 筆） |

也就是說，重試機制在這份樣本裡沒有幫上第三方任何一次，而在訂閱線上，它做的是：

- 對已經被限流的端點多打 63 次請求（21 筆 × 2 次額外重送）
- 在 Claude Code 顯示倒數之前，多壓 3.5～9.4 秒

最極端的一筆（`id: 2617`，一個 `messages: 1 / max_tokens: 1` 的內部探針請求）被 429
兩次、在 router 裡耗掉 5.003 秒，client 才自己放棄 —— 那 5 秒完全是 router 自己
製造的延遲。這組數字是 `src/routing.mjs` 與 `src/config.mjs` 裡「訂閱線預設關掉
429 重送」（`passthrough.retry.retryRateLimit = false`）這個決定的依據。

## Provider 串流：長連線沒有異常

Kimi K3 實測最長一筆串流 622 秒仍正常完成，過程中沒有出現靜默斷流。這是
