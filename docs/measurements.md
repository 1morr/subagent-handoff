# 實測數據

router 行為決定背後的量測本身。

## 基準：2711 筆真實流量

一份跑了 2711 筆真實流量的 `traffic.log`（29 個 session、3 個專案）：

| 指標 | 數字 |
| --- | --- |
| main（走訂閱） | 1043 筆 |
| subagent（走 Kimi） | 1668 筆 |
| 分流準確度 | 100% |

## router 自己重送：純損耗

router 曾經在上游回 `408` / `5xx` / `529` / 第三方 `429` 時自己先重送 2 次。同一份
記錄裡，22 筆觸發了重送（2026-09 從原始 `traffic.log` 重算）：

| 指標 | 數字 |
| --- | --- |
| 在訂閱線 | 22 / 22（100%） |
| 最後結果 | 21 筆仍是 429，1 筆 client 先放棄 |
| 帶了 `retry-after` | 0 / 22 |
| 請求是 `max_tokens: 1` 的小探針 | 22 / 22 |
| 同期第三方線的 5xx 或連線錯誤 | 0（共 1668 筆） |

也就是說，重送在這份樣本裡沒有幫上任何一次，而它做的是：

- 對已經被限流的端點多打 44 次請求（22 筆 × 2 次額外重送）
- 在 Claude Code 顯示倒數之前，多壓 3.5～9.4 秒

最極端的一筆（`id: 2617`）被 429 兩次、在 router 裡耗掉 5.003 秒，client 才自己
放棄 —— 那 5 秒完全是 router 自己製造的延遲。

再加上 Claude Code 本來就會對同一批狀態自己退避重試（見
[reliability.md](reliability.md)），router 已經拿掉這一層。

## Provider 串流：長連線沒有異常

Kimi K3 實測最長一筆串流 622 秒仍正常完成，過程中沒有出現靜默斷流。router 當時在
provider 線上游安靜超過 60 秒時會補 `event: ping`，同一份 1668 筆裡一次都沒觸發；
加上它在預設逾時下不改變結果（見 [reliability.md](reliability.md)），已經拿掉。
